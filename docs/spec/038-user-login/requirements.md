# 要件定義: ユーザーのログインと、手持ちの服のユーザーごとの紐づけ

- ステータス: approved
- 作成日: 2026-10-08
- 更新日: 2026-10-09(ゲストの扱い・写真の読み込み方を追記)

## 1. 背景 / 課題

手持ちの服(spec 010)は、写真と属性を 1 か所(spec 036 の Cloud Storage の `wardrobe/`)にまとめて保存している。

- アプリを使う人が全員、同じ「手持ちの服」を見て、登録・削除できてしまう。誰かが登録した服が、別の人のコーデ提案に使われる。
- 一方で、服を登録した人が後でアプリを開き直したときに、自分の服がそのまま残っていてほしい。

そこで、**ログインした人には、自分の服をずっと保存できる便利さを提供する**。ログインしない人(ゲスト)も今までどおり服の登録とコーデ提案を使えるが、服はそのブラウザだけで、1 日で消える。

ハッカソンのデモ用のため、ユーザー登録の画面は作らず、**運営側で事前に登録したユーザーだけがログインできる**ようにする。
spec 036 で、保存先の中の置き場所(接頭辞)を、ユーザーごとに分けやすい形にしてある。

## 2. ゴール / 非ゴール

### ゴール
- 運営側が事前に登録したユーザーが、ユーザー ID とパスワードでログイン・ログアウトできる。
- ログインの仕組みはアプリの中に自前で作る(外部の認証サービスは使わない)。パスワードはそのまま保存せず、元に戻せない形(ソルト付きのハッシュ)で保存する。
- 運営側がユーザーを追加・削除・パスワード変更できる手段(コマンド)を用意する。
- **ログインしたユーザー**の手持ちの服は、ユーザー専用の置き場所に保存し、ずっと残る。どの端末・ブラウザからログインしても同じ服が見える。
- **ログインしない人(ゲスト)** も、今までどおり手持ちの服の登録とコーデ提案を使える。ゲストの服は、ブラウザごとに発行するゲスト番号の置き場所に保存し、**登録から 1 日で自動的に消える**。同じブラウザなら、再読み込み・開き直しても 1 日以内は残る。
- 他の人(他のユーザー・他のゲスト)の服は、一覧に出ず、写真も取得・削除できない。
- MV 検索・カルチャー情報・ライブ情報・会場の形態は、今までどおりログインなしで使える(変更なし)。
- 今の画面のデザイン(spec 015)に合わせたログインの画面を作る。ログイン中は、誰でログインしているかが分かり、ログアウトできる。ゲストのときは、服が 1 日で消えることと、ログインすると残せることが分かる。
- ブラウザを再読み込み・開き直しても、7 日間はログインしたままにする。期間が過ぎたら、もう一度ログインを求める(その間はゲストとして使える)。
- 写真は、画面が API から(ログイン・ゲストの証明を付けて)取得して表示する。写真の URL を知っているだけでは見られない。
- 保存先がローカル(`WARDROBE_STORAGE=local`)でも Cloud Storage でも、同じようにユーザー・ゲストごとに分かれる。
- CLI のエージェント(spec 006)は、どのユーザーの服を読むかを指定できる。

### 非ゴール
- ユーザー登録(サインアップ)の画面。パスワードを忘れたときの再設定、利用者自身によるパスワード変更。
- Google アカウントなどでのログイン、メール認証、二要素認証。
- 管理者と一般ユーザーのような権限の区別。
- ゲストのときに登録した服を、ログインしたときにそのアカウントへ移すこと。
- ログイン前に登録された服(spec 036 の共有の置き場所 `wardrobe/`)の引き継ぎ。本番は動作確認用のデータしか無いため、使わなくなる。
- 知らない人による利用(費用)の対策、ログインの総当たり攻撃への対策。提出後の利用者は審査員程度と見込むため(2026-10-09 決定)。
- 複数の端末でのログイン状態の一覧や、強制ログアウト。

## 3. ユーザーストーリー

- `アプリの利用者` として、`ログインして、自分の手持ちの服を一度登録したら、次に開いたときもそのまま使える` ようにしたい。なぜなら `毎回写真を登録し直すのは手間` だから。
- `アプリの利用者(審査員など)` として、`ログインしなくても、服の登録からコーデ提案まで一通り試せる` ようにしたい。なぜなら `アカウントが無くてもアプリを評価したい` から。
- `アプリの利用者` として、`他の人が登録した服が、自分の一覧やコーデ提案に混ざらない` ようにしたい。
- `運営(開発メンバー)` として、`デモで使うアカウントを事前に用意` したい。

## 4. 受け入れ基準

- [x] AC-1: Given 運営側がコマンドでユーザーを登録した状態, When そのユーザー ID と正しいパスワードでログインすると, Then ログインでき、画面に誰でログインしているかが出る。
- [x] AC-2: Given 登録済みのユーザー, When 誤ったパスワード、または登録されていないユーザー ID でログインすると, Then ログインできず、どちらが誤っているか分からない文言(「ユーザー ID またはパスワードが違います」など)が出る。
- [x] AC-3: Given ユーザーの保存先, When 中身を見ると, Then パスワードがそのまま書かれていない(ソルト付きのハッシュだけ)。
- [x] AC-4: Given ユーザー A でログインして服を登録した状態, When 7 日以内に別のブラウザで A としてログインすると, Then 同じ服が一覧に出て、コーデ提案に使える。1 日以上たっても消えない。
- [x] AC-5: Given ログインしていない状態, When 服を登録してコーデ提案をすると, Then 今までどおり使える。服はゲストの置き場所(例: `guests/<ゲスト番号>/wardrobe/`)に保存される。
- [x] AC-6: Given ゲストとして服を登録した状態, When 同じブラウザで再読み込み・開き直すと, Then 1 日以内なら服が残っている。別のブラウザ・シークレットウィンドウでは見えない。
- [ ] AC-7: Given ゲストの服, When 登録から 1 日たつと, Then 保存先から自動的に消える(Cloud Storage の場合。ローカルの保存先では消えなくてよい)。
- [x] AC-8: Given ユーザー A・ユーザー B・ゲストがそれぞれ服を登録した状態, When それぞれで一覧を開く・コーデ提案をすると, Then 自分の服だけが使われる。他の人の服の ID や写真名を指定しても、取得・削除できない(404)。
- [x] AC-9: Given ユーザー A が服を登録した状態, When 保存先を見ると, Then A 専用の置き場所(例: `users/<A の ID>/wardrobe/`)に保存されている。ローカルと Cloud Storage のどちらでも同じ。
- [x] AC-10: Given ログイン・ゲストの証明が無い、または期限切れ・改ざんされた状態, When 手持ちの服・コーデ提案の API を呼ぶと, Then 401 になり、何も保存・取得されない。画面は(ログインの期限切れなら)ゲストとして使える状態に戻り、ログインを促す。
- [x] AC-11: Given ログインした状態, When ブラウザを再読み込み・開き直すと, Then 7 日間はログインしたままになっている。ログアウトするか期限が切れると、ゲストの状態に戻る。
- [x] AC-12: Given ログインした状態, When ログアウトすると, Then そのユーザーの服の表示が消え、ゲストの状態(ゲストの服)に戻る。MV やライブの入力は残る。
- [x] AC-13: Given 写真の URL, When ログイン・ゲストの証明を付けずに開くと, Then 写真は見られない(401)。画面では、登録した服の写真が今までどおり表示される。
- [x] AC-14: Given ログインの画面, When スマホの幅と PC の幅で開くと, Then 今の画面と同じ配色・カードのデザインで表示される。ゲストのときは、服が 1 日で消えることが分かる表示がある。
- [x] AC-15: Given 運営のコマンド, When ユーザーを追加・削除・パスワード変更すると, Then すぐにログインに反映される(サーバーの再起動は不要)。パスワードはコマンドの引数や履歴に残らない形で入力する。
- [x] AC-16: Given CLI のエージェント, When ユーザーを指定して手持ちの服を聞くと, Then そのユーザーの服を答える。
- [x] AC-17: Given MV 検索・カルチャー情報・ライブ情報・会場の形態, When ログインせずに使うと, Then 今までどおり使える。
- [x] AC-18: Given 自動テスト, When pytest / flutter test を実行すると, Then ログイン・ログアウト・ゲスト・401・ユーザーごとの分離を、外部サービスを呼ばずに確認できる。
- [x] AC-19: Given README, When チームメンバーが読むと, Then ユーザーの追加方法、ログインとゲストの仕組み、ローカルでの動かし方が分かる。

## 5. 制約 / 前提

- ログインの仕組みは自前で作る(2026-10-08 決定)。Firebase Authentication などの外部サービスは使わない。
- ユーザー登録の画面は作らない。ユーザーは運営側が事前に登録する(2026-10-08 決定)。
- ゲストも服の登録とコーデ提案を使える。ゲストの服は 1 日で消える。ゲストからログインへの服の引き継ぎはしない(2026-10-09 決定)。
- ゲストの服を消すのは、Cloud Storage のライフサイクルルール(作成から 1 日たったオブジェクトを自動で削除する設定)を使う見込み。1 日が設定できる最短の単位で、「最後に使った日から」ではなく「作成した日から」数える。
- 写真の読み込みは、画面が API から証明を付けて取得する方式にする(2026-10-09 決定。設計で検討した案 A)。画面(Firebase Hosting)と API(Cloud Run)のドメインが違うため、Cookie は使わない。
- ログイン状態とゲスト番号はブラウザに保存する。Flutter の `shared_preferences` を追加する見込み(依存の追加は design.md の承認時に確認する)。
- 本番の通信は HTTPS(Cloud Run と Firebase Hosting の既定)。トークンの署名に使う秘密の鍵は、Git にも `env.deploy.yaml` にも書かない(本番は Secret Manager から渡す。spec 035 の YouTube のキーと同じ方式)。
- パスワードやトークンをログに出さない。
- 依存する spec: 006(エージェントの服の参照)、010(手持ちの服の登録)、011(コーデ提案)、015(画面のデザイン)、035(デプロイ)、036(保存先。ユーザーごとの置き場所の土台)。spec 036(PR #14)のマージが前提。
