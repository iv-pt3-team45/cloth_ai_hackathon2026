# 要件定義: 手持ちの服の Cloud Storage への保存(F06)

- ステータス: approved
- 作成日: 2026-10-08
- 更新日: 2026-10-08

## 1. 背景 / 課題

手持ちの服(spec 010)は、写真と属性の一覧(`index.json`)をサーバー内のファイル(`backend/data/wardrobe/`)に保存している。

- 本番の Cloud Run では、**再デプロイやしばらくアクセスが無くてサーバーが止まるたびに、登録した服が消える**(spec 035 の決定事項 4)。デモの直前に登録し直す運用になっている。
- 登録した服がサーバーごとに分かれてしまうため、Cloud Run の最大インスタンス数を 1 に固定している(spec 035 の決定事項 5)。
- spec 035 の未決事項 2 で、Cloud Storage への移行は F06 の担当が行うことになっている。

保存処理はすでに `WardrobeStore`(Protocol)で抽象化されており、ローカルファイルの実装(`LocalWardrobeStore`)だけを持っている。今回はここに Cloud Storage の実装を足す。

将来、ログイン機能を入れて、登録した服をユーザーごとに分ける予定がある(別の spec)。今回はその前段として、保存先を Cloud Storage に移すところまでを行う。

## 2. ゴール / 非ゴール

### ゴール
- 設定で保存先を「ローカル」か「Cloud Storage」に切り替えられる。Cloud Storage のときは、手持ちの服の**写真と `index.json` の両方**をバケットに保存し、一覧・写真の表示・削除もバケットから行う。
- **既定はローカル**。設定を変えなければ、ローカル開発・Docker Compose・テスト・CI の動きは今と変わらない。
- 画面(frontend)と API(パス・リクエスト・レスポンスの形)は変えない。利用者から見た動きは、保存先がローカルのときと同じ。
- 本番(Cloud Run)では Cloud Storage を使うように設定し、再デプロイやサーバーの停止後も、登録した服が残る。
- エージェントの服の参照(spec 006 の `list_wardrobe` / `search_wardrobe`。CLI から使う)も、同じ設定でローカルと Cloud Storage を切り替える。Cloud Storage のときは、アプリで登録した服をバケットから読んで答える。CLI で `--index <パス>` を指定したときは、今までどおりそのローカルのファイルを読む。
- バケットは非公開にする。写真は今までどおり backend の API(`GET /api/v1/wardrobe/images/...`)を通して返す。
- バケットの中の置き場所は、1 つの接頭辞(例: `wardrobe/`)の下にまとめる。ログインを入れるときに、ユーザーごとの置き場所に分けやすくするため。
- バケットの作成と権限の付け方を、手順として README に残す。

### 非ゴール
- ログイン機能と、登録した服とユーザーの紐づけ(次の spec で扱う)。
- 今サーバー内にある服のデータを Cloud Storage へ移すこと(本番は現在 0 件。spec 035 の決定事項 4)。
- Cloud Run の最大インスタンス数の引き上げ(spec 035 の決定事項 5)。今回の変更で引き上げられる状態にはするが、実際に変えるかは清水が判断する。
- Firestore などのデータベースの導入。

## 3. ユーザーストーリー

- `アプリの利用者` として、`一度登録した手持ちの服が、時間をおいて開いても残っている` ようにしたい。なぜなら `毎回写真を登録し直すのは手間` だから。
- `開発メンバー` として、`ローカルでは今までどおりファイルに保存して開発` したい。なぜなら `Cloud Storage の準備なしで動かしたい` し、`テストで外部サービスを呼びたくない` から。
- `デモの担当` として、`デモの直前に服を登録し直さなくても済む` ようにしたい。
- `開発メンバー` として、`アプリで登録した服を、CLI のエージェントが Cloud Storage から読んで答える` のを確かめたい。なぜなら `保存先を移しても、エージェントから同じ服が見えることを確認したい` から。

## 4. 受け入れ基準

- [x] AC-1: Given 保存先の設定をしていない(既定)状態, When 服の写真を登録・一覧・削除すると, Then 今までどおり `backend/data/wardrobe/` に保存され、既存のテストがすべて通る。
- [x] AC-2: Given 保存先を Cloud Storage にしてバケットを指定した状態, When 服の写真を登録すると, Then 写真と `index.json` がバケットの接頭辞の下に保存され、サーバー内の `data/wardrobe/` には何も書かれない。
- [ ] AC-3: Given AC-2 で登録した状態, When 一覧を開く・写真を表示する・コーデを提案する(着せた画像の生成を含む)と, Then バケットの写真と `index.json` を使って、ローカルのときと同じ結果が返る。
- [x] AC-4: Given AC-2 で登録した状態, When 服を 1 点削除すると, Then `index.json` から消え、写真に服が残らなければバケットの写真も消える。
- [ ] AC-5: Given Cloud Storage を使う設定, When サーバーを再起動する(Cloud Run の再デプロイを含む)と, Then 登録した服がそのまま一覧に出る。
- [x] AC-6: Given Cloud Storage を使う設定, When バケットに接続できない・権限が無い場合, Then 利用者には今の保存失敗と同じ形のエラー(5xx)が返り、ログに原因が出る。アプリ全体は落ちない。
- [x] AC-7: Given 2 つのリクエストがほぼ同時に服を登録した場合, When 両方が終わると, Then 片方の登録が `index.json` から消えることはない(サーバーが複数台になっても成り立つ)。
- [x] AC-8: Given バケット, When 認証なしで中身の URL を開こうとすると, Then 見られない(非公開)。
- [x] AC-9: Given Cloud Storage を使う設定でアプリから服を登録した状態, When CLI のエージェント(`scripts/run_agent.py`)に「手持ちの服を教えて」「白い服はある?」と聞くと, Then バケットの `index.json` を読んで、登録した服を答える。
- [x] AC-10: Given 保存先の設定をしていない(既定)状態、または CLI で `--index <パス>` を指定した状態, When エージェントに手持ちの服を聞くと, Then 今までどおりローカルのファイルを読んで答える。
- [x] AC-11: Given 自動テスト, When `pytest` を実行すると, Then Cloud Storage を実際には呼ばずに(偽物に差し替えて)Cloud Storage 版の保存・一覧・削除・写真の読み出しと、エージェントのツールの参照を確認できる。
- [x] AC-12: Given README, When チームメンバーが読むと, Then 保存先の切り替え方、バケットの作り方と必要な権限、本番での設定が分かる。

## 5. 制約 / 前提

- GCP プロジェクト: `ai-agent-hackathon-508804`。バケットのリージョンは Cloud Run と同じ `asia-northeast1`。
- 認証は ADC(ローカルは `gcloud auth application-default login`、Cloud Run は実行用のサービスアカウント)。キーファイルは使わない。
- Cloud Run の実行用サービスアカウントは既定の Compute Engine サービスアカウント(spec 035 の決定事項 2)。このアカウントに、今回のバケットだけを読み書きする権限を付ける(プロジェクト全体の権限は付けない)。
- 依存ライブラリ `google-cloud-storage` を backend に追加する(2026-10-08 承認済み)。
- バケットの作成と権限の設定は、Claude が gcloud で行う。実行前にコマンドを提示して承認を得る(2026-10-08)。
- 外部 API を呼ぶテストは書かない(CLAUDE.md)。
- 依存する spec: 006(エージェントの服の参照)、010(手持ちの服の登録)、011(コーデ提案。保存した写真を使う)、035(Cloud Run へのデプロイ)。
