# 要件定義: 会場情報取得(F14)

- ステータス: draft
- 作成日: 2026-09-29
- 更新日: 2026-09-29(F15着手時に位置情報の取得を追加)

## 1. 背景 / 課題

コーディネート提案(F20: 統合スタイルプロファイル生成)は、会場・天気情報を統合して提案の材料にする設計になっている。そのうち「会場の形態(スタンディング/着席等)」を取得するのがF14の役割。現時点でF14・F15・F16はいずれも未実装。

追記: F15(天気情報取得)の入力は「会場の位置情報・公演日時」であり、F15はF14に依存する設計になっている。当初のF14は形態のみを扱う想定だったが、F15が必要とする位置情報もF14側で取得する形に変更する(会場名から位置情報を得る処理はF14の「会場について調べる」という役割と自然に一致するため)。

本来F14は、F08(公演URL解析)またはF09(手動入力フォールバック)が出力する「会場名」を入力として受け取る想定だが、F08・F09もまだ未実装のため、本specでは会場名を直接引数として受け取る形からスタートする。

## 2. ゴール / 非ゴール

### ゴール
- 会場名(文字列)を入力として受け取り、会場の形態(スタンディング/着席/不明など)を含む会場情報を取得できるようにする。
- あわせて、F15(天気情報取得)が必要とする会場の位置情報(住所、可能であれば緯度経度)も取得できるようにする。取得できない場合は空(不明)として扱い、F15側でのフォールバックに委ねる。
- 既存の実装パターン(`services/wardrobe.py` 等)に合わせ、「コアロジック関数」と「ADKツールとして登録する薄いラッパー関数」を分離して実装し、呼び出し方(エージェントの自律呼び出し / Orchestratorからの明示呼び出し)を問わず再利用できる形にする。
- 取得に失敗しても例外で落とさず、「形態不明」として扱ってサービス全体を止めない。

### 非ゴール
- F08(公演URL解析)・F09(手動入力フォールバック)との結合は対象外(会場名の入力手段は別spec)。
- F20への実際の受け渡し方式の確定は対象外(本specはF14単体のロジック実装まで)。

## 3. ユーザーストーリー

- `コーディネート提案の仕組み(エージェント/Orchestrator)` として、`会場名から会場の形態を把握` したい。なぜなら `会場の形態(スタンディング/着席等)がコーディネート提案の判断材料になる` から。

## 4. 受け入れ基準

- [x] AC-1: Given 会場名(例: "日本武道館")が渡されたとき, When 会場情報取得のコア関数を呼び出すと, Then 会場の形態を含む会場情報が返る。
- [x] AC-2: Given Gemini APIからの取得に失敗する状況(異常系), When 関数を呼び出すと, Then 例外を投げず「形態不明」として扱った結果を返す。
- [x] AC-3: Given 実装したコード, When `wardrobe.py`等の既存実装と比較すると, Then コアロジック関数とADKツール登録用ラッパー関数が分離されている。
- [x] AC-4: Given 会場名が渡されたとき, When 会場情報取得のコア関数を呼び出すと, Then 可能な範囲で住所(または緯度経度)を含む会場情報が返る。取得できない場合は空(不明)として返り、例外は投げない。

## 5. 制約 / 前提

- 技術制約: Gemini API(URL Context または Web検索)を使用する。既存のADC認証パターンをそのまま利用し、追加の外部APIキーは不要。
- 依存する spec: なし(F08/F09未実装のため、会場名は直接引数として受け取る)。
- 参考: 機能一覧表(ライブ用服装エージェント_機能一覧.xlsx) F14行、検討メモ(work_space/検討/F14-16_MVP優先度検討メモ.md)。
