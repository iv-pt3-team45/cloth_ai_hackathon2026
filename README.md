## アプリの概要

初めてライブに行く人の「何を着ていけばいい?」に答えるアプリ。
好きなアーティストの **MV**、行く **ライブ**、**手持ちの服の写真** の 3 つを入れると、
AI(Gemini)がアーティストのファッションの傾向・会場・当日の天気を踏まえて**手持ちの服の中から**コーデを 1 つ組み、
マネキンに着せた画像で見せる。

### 使い方

画面は 1 ページで、上から順に入力していく(上部の段階表示が「1 入力 → 2 AIが考え中 → 3 提案」と進む)。

| 入力 | 利用者がやること | AI・アプリがやること |
| --- | --- | --- |
| ① MV を選ぶ | YouTube の URL か MV 名を入れる | 曲名・アーティスト名を取り出し、アーティストのファッション(スタイル・よく使う色・定番のアイテム)、その MV の衣装、経歴・音楽性を Google 検索と MV の映像から調べる。画面の配色・背景もアーティストの雰囲気に合わせて変わる |
| ② 行くライブを検索 | ライブ名・ツアー名・会場か公演日を入れて、候補から選ぶ | 該当するライブを最大 3 件探し、会場・公演日・当日の天気(過去の公演なら実績、2 週間先までなら予報)を出す。会場がスタンディングか着席かも裏で調べて提案に使う |
| ③ 手持ちの服 | 服の写真を登録する(1 回 10 枚まで) | 写真から服ごとに種類・素材・色・柄・系統・季節・暖かさ・使う場面を読み取って保存する |

3 つそろったら「**コーディネートを提案してもらう**」を押す。

1. AI が手持ちの服から 1 コーデを選ぶ(数秒〜十数秒)。手持ちに無い服は提案に入れない。
2. 選んだ服をマネキンに着せた画像を作る(十数秒〜数十秒)。
3. コーデ名・着せた画像・使う服(役割と理由)・選んだ理由とポイント・MV のファッション・会場と天気が表示される。
   画像はタップで拡大でき、Web では保存できる。「条件を変えてもう一度」で入力に戻ってやり直せる。

### ログインとゲスト

ゲストでもすべての機能を使える。違うのは登録した服の残り方だけ。

| | ログインしたユーザー | ゲスト |
| --- | --- | --- |
| なれる人 | 運営が事前に登録したユーザーだけ(新規登録は受け付けていない) | 誰でも(開くと自動でゲストになる) |
| 登録した服 | 削除するまで残る。別の端末でログインしても同じ服 | 登録から 1 日で消える(同じブラウザでだけ見える) |

服の写真は持ち主本人だけが見られる。データの扱いは、画面の一番下の「プライバシーポリシー」に書いてある。

### 知っておくこと

- ① のカルチャー情報と ② のライブの検索は数十秒かかり、その間は ① ② の入力を受け付けない。
- 「この MV の衣装」は公開動画でしか読み取れない(非公開・限定公開・年齢制限のある動画では出ない)。
- カルチャー情報・ライブ情報は保存せず、選ぶたびに調べ直す。提案の履歴も残らない(もう一度提案すると前の結果は置き換わる)。

### 4.6 服画像のインデックスを作る

服の写真から**素材・形・色・系統・季節・暖かさ・使う場面**などを抽出して JSON にする。
(アプリから自分の服を登録する場合は 4.11。この CLI は開発用のサンプル作成に使う)



```json
{
  "generated_at": "2026-09-17T15:43:10+09:00",
  "model": "gemini-3.5-flash-lite",
  "source_dir": "tests/sample_images",
  "count": 5,
  "entries": [
    {
      "image": "image.jpeg",
      "items": [
        {
          "category": "Tシャツ",
          "material": "綿",
          "shape": "半袖クルーネック",
          "colors": ["ピンク", "黄色", "赤"],
          "pattern": "プリント",
          "style": "カジュアル",
          "notes": "「Let's Eat」と書かれた円形プリント",
          "seasons": ["春", "夏"],
          "warmth": "薄手",
          "occasions": ["普段着"]
        }
      ],
      "summary": "床に広げられたピンクの半袖Tシャツ。",
      "model": "gemini-3.5-flash-lite",
      "analyzed_at": "2026-09-17T15:42:54+09:00"
    }
  ]
}
```

- 1 枚に複数の服が写っていれば `items` が複数件になる。
- **処理済みの画像は再実行時にスキップする**(`index.json` にある画像名で判定)。作り直すときは `--force`。
- 解析 1 枚ごとに `index.json` を書き出すので、途中で中断しても解析済みは残る。
- 画像以外のファイルは無視する。1 枚の解析に失敗しても残りは処理を続ける。
- 抽出項目を増やすときは [app/services/cloth_index.py](backend/app/services/cloth_index.py) の `ClothItem` に追加する。
- 季節・暖かさ・使う場面は決まった選択肢(4.11)。選択肢の外の値は捨てる。


### 4.15 プライバシーポリシー

利用者の服の写真を扱うため、アプリ内にプライバシーポリシーの画面がある(spec 042)。

- 初期ページ(入力の段階)の一番下、③ 手持ちの服のカードの下に、小さな灰色の文字で「**プライバシーポリシー**」がある
  (カードの外の文字なので、MV に合わせた暗い背景では明るい色になる。spec 041)。
  押すとアプリ内の画面が開き(全文を 1 つの枠にまとめ、節は「1. はじめに」のような見出しで分ける。配色は入力の画面を引き継ぐ)、
  ← またはブラウザの戻るで初期ページに戻る(入力は残る)。AI が考え中・提案の段階には出ない。
- 文は `frontend/lib/features/privacy/privacy_policy.dart` の `policySections` にある。運営者(`policyOperator`。「テックドロップ」)と
  制定日(`policyEstablished`)も同じファイルの定数。問い合わせ先の項目は無い。
- 内容は **今の main の実装**(ログインしたユーザー・ゲストごとに服を分け、本人だけが見られる・ログインしたユーザーの服は削除するまで残り、ゲストの服は自動で消える・パスワードはハッシュで保存・新規登録の画面は送らない・外部のサービスに送る。3.6)に合わせて書いている。
  外部のサービスの名前や保存の日数などの具体的な値は書かず、「AI のサービス」「しばらくのあいだ」のような一般的な言い方にしている
  (テストで、サービスの名前や日数が入っていないことも確かめている)。

> **データの扱いを変えたら、同じ変更でポリシーも直す。** 保存先・共有の範囲・保存期間・送り先の外部サービス・集める情報を変える spec は、
> `privacy_policy.dart` と `frontend/test/privacy_policy_test.dart` も直すこと(例: 新規登録を受け付けるようにしたら、集める情報と保存の仕方を書き足す)。

## 6. SPEC 駆動開発の進め方

機能ごとに `docs/spec/<連番>-<機能名>/` を作り、**要件 → 設計 → タスク → 実装** の順で進める。
詳細は [docs/spec/README.md](docs/spec/README.md)、雛形は [docs/spec/_template/](docs/spec/_template/)。

```
docs/spec/001-user-authentication/
├── requirements.md   # なぜ / 誰が何をできるか / 受け入れ基準(AC)
├── design.md         # どう作るか(API・データモデル・画面・エラー・テスト方針)
└── tasks.md          # 30〜90 分粒度の作業分解(チェックボックス)
```

原則:

1. **requirements.md が承認されるまで design.md を書かない。design.md が承認されるまで実装しない。**
2. 受け入れ基準(AC)はテスト可能な粒度で書き、`tasks.md` の各タスクから参照する。
3. 実装中に設計が変わったら、コードと同じコミットで `design.md` を更新する。
4. 機能完了時に本 README の機能一覧 / アーキテクチャを更新する。
5. ブランチ名は spec 名に揃える(例: `feat/001-user-authentication`)。
